# LocalCore

LocalCore 是一个运行在手机本地的专业 LLM 后端，同时提供必要的管理 UI。它的主要用途不是在手机上实现一套聊天前端，而是在手机本地加载 GGUF 模型，并向其他客户端稳定提供推理能力。

项目的最高优先级是减少重新编译。应用只固化无法动态化的最小运行骨架和必要线路；模型定义、Jinja 模板、推理参数、下载来源、服务配置、更新策略以及适合声明式表达的 UI，尽量由运行时配置和可更新资源提供。能够通过配置或动态资源完成的变化，不应通过新增硬编码页面、按钮或业务分支完成。

## 核心目标

- 在 Android 手机上本地加载和运行 GGUF 模型。
- 提供专业、稳定、可观测的本地后端服务，而不是聊天客户端。
- 统一支持 llama.cpp 的 Jinja 模板能力；每个模型绑定并使用自己的模板，不存在所有模型共用一个模板的设计。
- 支持模型及相关资源的自动下载、断点续传、完整性校验和版本管理。
- 支持动态核心和配置资源自动更新，以减少因业务调整、参数变化或界面扩展而重新编译 APK。
- 提供最小但足够的管理 UI，用于查看状态、编辑配置、管理模型、控制服务、查看错误和执行更新。

## 第一原则：减少编译

LocalCore 的结构以“哪些内容必须编译”为边界，而不是以前端页面或传统业务模块为边界。

只有下面这些能力应进入静态 APK 骨架：

- Android 应用生命周期和后台运行所需的系统集成。
- GGUF 推理运行时及其必要的原生接口。
- 文件、网络、下载、权限和本地服务等平台能力。
- 动态核心、配置和资源的加载、校验、激活与更新入口。
- 在动态内容不可用时能够直接暴露真实错误的最小诊断入口。

下面这些内容原则上应保持动态，不因普通调整触发 APK 编译：

- 模型注册信息和下载地址。
- 每个模型独立绑定的 Jinja 模板。
- 模型加载参数、推理参数、停止词和能力声明。
- HTTP 服务参数和协议映射配置。
- 下载与更新策略。
- 日志和诊断配置。
- 可以通过 Schema 或声明式配置生成的管理项和管理界面。
- 不依赖新增原生能力的业务逻辑与动态核心资源。

新增一个参数、模型、模板或常规管理项时，默认应当只修改 JSON、Jinja 或动态资源。只有新增 Android 平台能力、改变原生 ABI、升级必须重新链接的推理运行时，或者现有动态框架确实无法表达需求时，才允许重新编译。

## 产品边界

LocalCore 是“带 UI 的后端”，UI 是后端的本地管理控制台。

项目应包含：

- 后端运行状态和当前模型状态。
- 模型的注册、下载、校验、加载、卸载和切换。
- 服务地址、端口、鉴权及其他后端参数配置。
- 原始 JSON 配置查看、编辑、导入和导出。
- Jinja 模板绑定、查看和更新。
- 请求、推理、下载和更新错误的直接展示。
- 动态核心与配置资源的版本、更新和激活状态。

项目默认不包含：

- 面向聊天使用的消息页面和会话管理。
- 人设、角色、PAL、预设市场或社区系统。
- 登录、社交、云同步和内容展示业务。
- 为单个模型或单个功能硬编码的专用页面与按钮。
- 与本地后端无关的 PocketPal 前端功能。

## 配置驱动

配置是 LocalCore 的主要扩展接口，不是编译期常量的补充。

- 配置必须具有明确的 Schema 和版本。
- 每项配置只有一个权威数据源；UI、服务和动态核心读取同一份有效配置。
- 配置加载失败、字段非法、引用缺失或版本不兼容时必须直接报告具体错误，不得静默回退、吞掉异常或用猜测值继续运行。
- 配置更新必须先完成格式、Schema、引用和完整性校验，再进行原子激活；未通过校验的内容不能污染当前有效版本。
- UI 可以先不为每个配置项制作专用控件。项目早期优先提供统一的 JSON 编辑、校验、导入和导出能力。
- 后续确需图形化配置时，应由统一的 Schema/声明式 UI 系统生成，避免每增加一个参数就新增页面和按钮。

## 模型与 Jinja 模板

模型配置是模型运行所需信息的统一入口。每个模型应通过自己的配置声明：

- GGUF 文件和下载信息。
- 文件大小、摘要和版本信息。
- 绑定的 Jinja 模板或明确使用 GGUF 内嵌模板。
- 上下文、缓存、设备、线程和其他加载参数。
- 采样、停止条件、thinking、tool calling 等推理参数。
- 模型具备的能力以及所需的运行时兼容版本。

框架提供统一的 Jinja 执行能力，但不替模型选择或猜测模板。一个模型只能使用其有效配置明确绑定的模板，或者配置明确指定使用 GGUF 元数据中的模板。模板不存在、解析失败或与运行时不兼容时，模型不得以其他模板继续运行。

## 动态核心与自动更新

动态核心的目的就是减少编译。静态 APK 提供稳定宿主，能够动态加载、校验和激活的业务能力应放入版本化动态核心或配置资源中。

所有可更新内容都必须具有清晰的类型、版本、兼容范围、来源和完整性信息。更新流程应统一为：发现版本、下载到暂存区、校验内容、检查兼容性、原子激活、记录结果。任何步骤失败都应保留当前已确认有效的版本，并明确报告新版本未激活的原因；不能把失败更新伪装成成功。

动态更新不应绕过真实的原生兼容边界。涉及 Android 原生代码、ABI 或必须重新链接的推理库时，应作为 APK/原生核心更新处理；仅涉及模型、模板、参数、声明式 UI 或动态业务逻辑时，不应要求重新编译 APK。

## 参考 PocketPal 的原则

`D:\AI\LLM\pocketpal-experimental` 是能力参考，不是 LocalCore 的项目模板。

可以调查和移植对后端有直接价值的成熟实现，例如：

- GGUF 和 llama.cpp/llama.rn 集成。
- Android 后台下载、断点续传和下载状态持久化。
- 模型文件导入和存储处理。
- OpenAI 兼容请求、流式输出及工具调用所需的协议映射。
- 已经由事实证明必要的 Android 原生适配。

不得照搬它的聊天前端、PAL、预设、账户、社区等业务，也不得复制其把 UI 状态、模型状态、下载状态、模板和推理生命周期糅合在同一 Store 或页面中的结构。移植前必须先确定能力边界，再把实现收敛到 LocalCore 的统一配置、统一模型入口和统一服务入口。

## 实施顺序

1. 建立最小 Android 宿主、动态核心加载入口和统一配置系统。
2. 接通单个 GGUF 模型的加载、卸载和推理生命周期。
3. 接通每模型独立 Jinja 模板及严格配置校验。
4. 提供最小后端 API 和流式响应。
5. 移植并整理后台下载能力，补齐完整性和原子安装流程。
6. 建立动态核心、模型、模板和配置资源的统一更新机制。
7. 提供通用 JSON 管理 UI，再按必要性增加声明式图形控件。

任何阶段都只实现当前阶段必需的线路。新需求优先扩展配置协议和统一运行框架，不通过不断增加特殊按钮、特殊页面和特殊分支推进项目。
